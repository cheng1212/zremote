## 一、总体结论

**基本健康，无 P0（致命），但"生命周期管理"是系统性短板。** 协议底子打得牢：信封解包、CAS 本地闸、分片重组、HMAC/wss、valueCodec 双端一致全部落实；测试文化好（Flutter 双绿、Web vitest 216 用例）；无硬编码凭据、无日志泄密。但**"断线恢复"和"切会话/切项目"两条生命周期路径是重灾区**：桥恢复后订阅静默冻屏、重连后"已连接"假象、切项目泄漏 Bridge、切会话污染附件 ref——外加一个**回滚可能打到错误回合的破坏性 bug**。

**总体评分：7/10。**

## 二、Top 5 最要命的问题

1. **[Web-P1-1] 回滚目标跨回合残留**——`web/src/stores/app.ts:891/937`。对 A 回合预览回滚后不重置，换 B 回合打开面板直接显示"确认回滚这一回合"，点确认会回滚 **A 回合**。破坏性操作打错对象，一次误滚即丢工作区文件。
2. **[协议-P1-1] 桥恢复后订阅静默失效 + 旧协议栈泄漏**——`web/src/protocol/remoteSession.ts:42-53`。`recoverOnce()` 成功后 `attach()` 用新 `RpcFrames`/`ChannelClient` 覆盖旧引用而不 dispose：旧栈的 30s cleanupTimer 永久泄漏；新栈 handlers 表为空，所有订阅帧被静默丢弃——网络抖动一次，当前会话即冻屏且无任何提示。`Subscription.resubscribe()` 全仓库零调用，恢复后无任何重建订阅的逻辑。
3. **[Web-P1-3] relay 重连后"已连接"假象**——`web/src/stores/app.ts:301`。自动重连只恢复 socket，不触发任何订阅校验/重建；ChatView 全文件零 `relayState` 引用，无连接指示；且全应用没有任何"断开" UI 入口（`disconnect()` 仅 `app.ts:1192` 一处定义）——用户只能刷新页面。
4. **[Web-P1-2] 附件 ref 跨会话污染**——`web/src/stores/app.ts:741/1103/1136`。违反 AGENTS.md"ref 是会话域"的铁律：A 会话上传中途切到 B 会话，上传完成把 A 的 ref 追加进 B 的待发送列表，在 B 发送会把 A 的附件带出去；`closeSession()` 也不取消在途上传。
5. **[Flutter-P1] 配对凭据明文存储仍未迁移**——`lib/ui/pair_page.dart:35/71`。完整配对链接（含 sid+hash，可冒充终端会话）明文存 SharedPreferences。AGENTS.md 登记的"对外分发前必须迁移 `flutter_secure_storage`"依然有效。注：Web 端已做到凭据只存 Pinia 内存、不落 localStorage（`web/src/stores/app.ts:314/354` 仅存 `lastWorkspaceKey`），反而更安全。

## 四、发现项：Web 协议层（`web/src/protocol/`）

### P1-1 桥恢复后订阅静默失效，且旧协议栈泄漏
- **位置**：`remoteSession.ts:42-53`（`Bridge.attach`）、`:112-113`（`recoverOnce`）、`subscription.ts:90`、`conversation.ts:136/177`、`rpcFrames.ts:37`
- **现象**：relay 断线重连（或 `bridge-degraded`）后 `recoverWithRetry()` 成功，当前会话的聊天帧、sessions-index 实时帧**全部停止推送，界面静默冻屏**；旧 `RpcFrames` 的 30s `cleanupTimer` 永久泄漏，旧 `ChannelClient` 的 handlers 永不释放。
- **根因**：`recoverOnce()` 成功后直接 `this.attach(info)`，`attach()` 只用新对象覆盖 `this.frames`/`this.channels`，**从不 dispose 旧栈**（`Bridge.dispose()` 只在 `RemoteSession.dispose()`:331-336 被调用）。`Subscription` 构造时捕获的是旧 `ChannelClient`（`conversation.ts:136`，监听器注册在 `subscription.ts:90`）；`dispatch()`（:253-264）把后续帧路由给新栈→新 `ChannelClient` handlers 表为空→所有事件被静默丢弃（`channelClient.ts:86` 为空即丢）。`resync()` 走旧 `ChannelClient` 发出，响应经新通道回来找不到 handler→挂满 30s 超时。
- **复现**：读 `recoverOnce`→`attach` 代码路径即确认；运行时制造一次 relay 重连，观察恢复成功后流式帧停止。
- **修复**：`attach()` 开头先 `this.frames.dispose(); this.channels.dispose()`；并在 `recoverOnce` 成功后通知上层重建订阅——最小改动是把 `Subscription` 持有的 `ch` 改为 `() => bridge.channels` 延迟取值，或在 `ConversationV4` 加 `onBridgeRecovered` 钩子调用现成的 `sub.resubscribe()`（该方法存在但全仓库零调用）。

### P1-2 `resync` 单飞闸在重试链中提前释放，并发 resync 可绕过
- **位置**：`subscription.ts:159-191`（`:190` 的 finally）
- **现象**：首次 resync 失败后，1s/2s 退避重试 pending 期间闸已被释放；窗口内新的断档判定可 `tryAcquire()`（:162）成功并发起第二次 resync，与待发动的重试链重叠——违背 `ResyncGate`（`lib/gates.ts`）"单飞"的设计承诺（该闸正是为修"同一毫秒 12 次并发 resync"事故而设）。
- **根因**：`.finally(() => { if (attempt === 0) this.gain.release() })` 在 attempt-0 settle 时立即执行，而重试是 `setTimeout(..., 1000 << attempt)`（:186）异步延后；attempt>0 按注释"不碰闸"→出现"闸已放、重试未发"空窗。
- **复现**：mock `ch.call` 让首次 `resyncConversationV4` 失败，在 catch 调度的 1s 内再调 `resync()`→第二次能拿到闸。
- **修复**：attempt-0 的 finally 中若已安排重试（`attempt < 2` 且失败）则不释放，由重试链终点释放；或让 `resync(attempt>0)` 也走 `tryAcquire`。

### P2-1 `RpcFrames.accept()` 在 messageSeq 复用时丢弃首片
- **位置**：`rpcFrames.ts:144-154`
- **现象**：同一 `messageSeq` 带不同元数据到达（服务端重启/桥恢复后计数器重置），旧 assembly 被删除**但当前分片也被丢弃**；后续分片建新 assembly 却永远缺第一片→`received < fragmentCount`→60s 后 `purge()` 静默清理。消息级静默丢失。
- **根因**：元数据不一致分支 `delete` 后直接 `return`，没落到"新建 assembly 并收片"逻辑。另 `checksum ?? null` vs `undefined` 比较（:151）：双方都不带 checksum 时 `null !== undefined` 恒真，会把同元数据的复用也误判为冲突。
- **修复**：冲突分支删旧 assembly 后不 `return`，继续走新建流程收下当前片；checksum 比较前归一化（两边统一 `?? null`）。

### P2-2 `RemoteSession.request()` 成功后超时 timer 不清除
- **位置**：`remoteSession.ts:204-211`
- **现象**：每次信令 request 成功 resolve 后，30s `setTimeout` 闭包仍挂起直到触发（靠 `completers.has` 空转一次）。`channelClient.call()`（:97-101）已用 `settle()` 正确清理，此处是同类代码遗漏。
- **修复**：保存 timer 句柄，resolve/reject 时 `clearTimeout`。

### P2-3 `Subscription.start()` 失败时事件监听器泄漏
- **位置**：`subscription.ts:90-107`
- **现象**：`addEventListener`（:90）先注册、`ch.call(subscribe)`（:93-98）后抛错（超时或 `missing ack.subscriptionId` :107）时，`cancelListener` 已赋值但永不调用；迟到帧持续 `staged.push`（:125），数组无界增长直到下次 `resubscribe`/`cancel`。
- **修复**：`start()` 失败路径调用 `this.cancelListener?.()` 并置空。

### P2-4 `ChannelClient.dispose()` 未清理在途 `call` 的超时 timer
- **位置**：`channelClient.ts:97-101`（timer）、`:218-224`（dispose）
- **现象**：桥切换/重建时 `dispose()` 会 reject `pending`（:220），但每个 `call` 闭包里的 30s `setTimeout` 没人清，占住 timer 句柄与闭包直到自然触发。
- **修复**：`pending` 条目附带 timer，`dispose()` 遍历清理（复用 `settle()` 的清理逻辑）。

### P2-5 `RelayClient.sendPayload()` 超 100 条静默丢弃
- **位置**：`relayClient.ts:159-166`
- **现象**：非 `paired` 状态下 outbound 队列满 100 后新 payload **无声丢弃**（丢弃时连日志都没有）。`RemoteSession.request()` 经此发送——长断线重连期间的请求直接蒸发，调用方只能等 30s 超时，难以定位。
- **修复**：丢弃时打日志（含计数）；或让 `sendPayload` 返回 boolean/抛错，使 `request()` 快速失败。

## 五、发现项：Web 状态层与 UI 层（`web/src/stores/app.ts`、`lib/`、`views/`、`components/`）

### P1-1 回滚目标跨回合残留（破坏性）
- **位置**：`app.ts:891`（`loadChanges`）、`ChatView.vue:61`（`openChanges`）、`FileChangesSheet.vue:20`（`previewed`）、`app.ts:937`（`applyRewind`）
- **现象**：对 A 回合"先看看回滚会影响什么"（`previewRewind` 写 `rewindTarget`/`rewindPreview`）后关闭；再对 B 回合打开文件变更面板，面板仍显示 A 的预览（`previewed = computed(() => app.rewindPreview != null)` 为真，跳过"先看看"直接显示"确认回滚这一回合"），点确认回滚 **A 回合**。
- **根因**：`rewindPreview`/`rewindTarget` 只在 `closeSession()`（经 `clearChanges()`）清零；`loadChanges()`（:891-912）只重置 `changes/changesError/changesLoading`；`openChanges()` 只调 `loadChanges()`。面板按"打开次数"复用，预览态按"会话"清，粒度错配。
- **复现**：进会话→点某回合文件徽章→"先看看"→关闭→点另一回合文件徽章→直接出现"确认回滚这一回合"（应重新出现"先看看"）。
- **修复**：`openChanges()` 或 `loadChanges()` 开头置空 `rewindPreview/rewindTarget`；或收敛进 FileChangesSheet 局部状态。

### P1-2 附件 ref 与上传态跨会话污染
- **位置**：`app.ts:741`（`closeSession`）、`:1103`（`uploadAttachment`）、`:1129-1148`
- **现象**：A 会话选文件上传中途返回进 B 会话，上传完成时 `this.pendingAttachments = [...this.pendingAttachments, res]`（:1136）把 **A 的 ref** 追加进 B 的待发送附件；在 B 发送会把 A 的 ref 带出去。违反"ref 会话域"铁律；上传进度条也会残留在新会话聊天页。
- **根因**：`closeSession()` 只调 `clearAttachmentState()`（仅清 `attachmentUrls/attachmentLoading/attachmentErrors`），不碰 `pendingAttachments`/`uploadPct`/`uploadName`/`uploadErr`，也不调用 `uploadCancel`（模块级变量无人调用）。
- **复现**：A 会话选稍大文件上传→中途返回→进 B 会话→等上传条走完→B 输入框上方出现 A 的附件 chip→在 B 发送。
- **修复**：`closeSession()` 调 `uploadCancel?.()` 并重置上传态；`uploadAttachment` 完成时校验会话 id 仍是发起会话，不一致则丢弃。

### P1-3 relay 重连后订阅无恢复 + ChatView 零连接指示
- **位置**：`app.ts:301`（`session.relay.onState(...)`）、`ChatView.vue`（全文件零 `relayState` 引用）、`conversation.ts:201/206`
- **现象**：relay 掉线后自动重连（`relayClient.ts:315-337` 指数退避），store 的 `onState` 回调只做 `this.relayState = session.relay.state`，不触发任何订阅校验/重建；`Subscription.resubscribe()` 在 `web/src` 零调用。重连后 `relayState` 回到 `paired` 显示"已连接"，但订阅可能已死：列表 phase 冻结、流式不更新。SessionsView 有"未连接"横幅，但 ChatView 顶栏只有 phase chip、**无任何连接状态提示**，发消息失败才后知后觉。
- **修复**：relay `reconnecting → paired` 跃迁时自动 `resyncIndex()` + 有打开会话则 `forceResync()`（或至少把横幅做到 ChatView）；给 SessionsView 加"断开重连"入口调 `disconnect()` 回 PairView。

### P1-4 草稿发送中途返回，仍被拽进新会话
- **位置**：`app.ts:971-1003`（`sendText` 草稿分支）
- **现象**：草稿页点发送→`createSession` 在途→用户按返回（`closeSession()`，chatMeta=null）→`await this.openSession(created, …)` 仍无条件执行，把用户拽进刚建的会话。
- **根因**：`createSession` 与 `openSession` 之间无"用户是否还在草稿流里"的有效性检查。
- **修复**：`openSession(created)` 前检查 `this.chatMeta` 是否仍为发起时的草稿（token/引用比对），失效则返回，会话留在列表由用户自己点。

### P2-1 `connect()` 失败泄漏整个 session
- **位置**：`app.ts:300-345`
- **现象**：`new RemoteSession` 后先 `this.session = session`；`await session.connect()`/`waitPaired`/`bootstrap` 任一步抛错，catch 只写 `failure` 就 rethrow——**从不 `dispose()`**。孤儿 session 的重连定时器/心跳继续跑；第二次 `connect()` 覆盖 `this.session`，旧对象永久泄漏；`relayState` 卡在 `'connecting'`；旧 `onState` 闭包还会往 store 写旧状态。
- **修复**：catch 里 `session.dispose()` 并置空 `this.session`、`relayState` 置 `'error'`。

### P2-2 `openWorkspace` 每次切项目泄漏一个 Bridge
- **位置**：`app.ts:347`；`remoteSession.ts:290/314`（`openBridge` push 进 `activeBridges`）
- **现象**：`openWorkspace` 只 `this.bridge = bridge` 覆盖引用，旧 Bridge 从不 dispose；`activeBridges` 只增不减。且 `onRelayState`（`remoteSession.ts:163-168`）在重连恢复时会对**已废弃的桥**也执行 `recoverWithRetry()`。
- **修复**：`openWorkspace` 开头 dispose 旧 bridge（或在 RemoteSession 加 `closeBridge` 并从 `activeBridges` 移除）。

### P2-3 `loadConfigOptions` 无代际守卫
- **位置**：`app.ts:815-845`
- **现象**：A 会话首帧触发 `loadConfigOptions()`（在途）→切 B 会话→B 首帧再触发→两次并发，**后返回的覆盖先返回的**。若 A 的响应晚于 B 到达，`configGroups/configTaskId` 是 A 的但看的是 B 的聊天页：顶栏 `modelTag` 显示 A 的模型；此时点"切换模型"，`applyModel` 用 A 的 provider/option 去切 B 的会话。
- **修复**：加递增 generation，RPC 返回后比对 `sid`/generation 再落盘；或单飞。

### P2-4 草稿页顶栏模型与实际要用的模型不一致
- **位置**：`app.ts:723`（`openDraft`）、`:823`（`if (!sid) return`）
- **现象**：`openDraft()` 不清空 `configGroups`；草稿无 taskId，`loadConfigOptions` 直接 return。于是顶栏 `modelTag` 和 ConfigSheet 选项/`current` 高亮全是**上一个会话**的，而草稿实际用工作区默认。用户以为"还是刚才那个模型"，首条消息可能进错模型。
- **修复**：`openDraft()` 清空 `configGroups/configTaskId`，草稿态顶栏显示"默认模型"；ConfigSheet 注明选项来自工作区级。

### P2-5 `uploadCancel` 模块级变量竞态
- **位置**：`app.ts:1108-1114`、`:1146-1148`
- **现象**：A 会话上传中途切 B 会话再传（两上传并发）→第二次调用覆盖 `uploadCancel`；第一个上传的 `finally` 执行 `uploadCancel = null`，即使 B 的上传还在飞——此后点"取消"无效果。
- **修复**：取消旗标收进会话级对象（`Map<sid, cancel>`），或 `finally` 里比对后再清空。

### P2-6 ChatView 输入框文字跨会话残留
- **位置**：`ChatView.vue:36`（`input` ref）、`App.vue:17`（`v-if="!app.chat"`）
- **现象**：`openSession` 同步执行 `this.chat = createConvState()`，切会话时 `app.chat` 从不经过 null→ChatView 不卸载→`input` ref 保留。A 会话打一半字不发送切到 B 会话，输入框还是 A 的字，误发即串会话。
- **修复**：监听 `chatMeta.sessionId` 变化清空 `input`（或 keyed 子组件）。

### P2-7 模型闸门首帧超时：注释与行为矛盾（颗雷）
- **位置**：`app.ts:977`
- **现象**：12s 首帧超时→`gotFrame=false`→注释写"闸门跳过"，但代码实际仍走 `checkModelGate(null, …)`（snapshot null→`ok:false` 拦截）。当前行为碰巧安全，注释是颗雷：将来有人"按注释"改成跳过，就会放行错模型。

### P2-2 `renameTask`/`archiveTask`/`unarchiveTask` 无软失败检查（BUG-14 纪律缺口）
- **位置**：`lib/state/app_controller.dart:1424-1432`（rename）、`:1668-1680`（archive）、`:2021-2028`（unarchive）
- **现象**：RPC 返回 `{ok:false}`（静默拒绝、不抛异常）时本地状态已被改写→**假成功**，直到下次 `loadTasks`/`pullLatest` 才恢复。`_isSoftFailure`（:1472-1478）只在 `setTaskPinned`:1454 使用；这三处是"RPC 后写本地"模式，同样没判软失败。

### P2-3 软失败识别口径不一致
- **位置**：`lib/protocol/conversation.dart:818-825`（`requireAccepted` 只看 `status` 字段）；`lib/state/app_controller.dart:1472-1478`（`_isSoftFailure` 看 `ok/accepted/success==false`）

- **修复**：`requireAccepted` 补 `ok/accepted/success==false` 判定，或收敛到同一函数。

### P2-4 `_keepSessionModel` 的 `recProvider` 空值未守卫

- **现象**：`sessionModels[sid]` 只有 `model` 无 `provider` 时，守恒器仍触发，发 `provider:''` 的纠正 RPC，可能被静默拒绝或误设；`_patchConfig` 空 provider 污染本地显示。守卫只检查 `recModel` 非空（:1622）。

### P2（建议级） `_notifiedTitles` 无上限无清理
