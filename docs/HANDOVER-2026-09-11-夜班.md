## 三、待办：图片上传（调研已完成，方案待批）

用户原话："图片上传 我改了很多次了都没改好……你自己去 github 找优秀项目
学习下 怎么上传 怎么回显 怎么预览"。**已按要求调研，未改代码。**

### 关键判断：前 4 轮全改错了地方
`docs/feat-image-*.md` 共 4 份（网格 / 画廊 / 去黑边 / 独立块）**全是展示层**，
`feat-image-standalone-blocks.md` 里自己写着「展示层改动，上传协议未动」。
展示早就打磨过了，**上传的根子一直是坏的**。

### 根因（3 个，都在上传链路）
1. **完全没有图片压缩，原图直传** —— `pubspec.yaml` 无任何图片库，
   `chat_page.dart` 无压缩逻辑。现代手机照片 3~12MB。
2. **分片上传没有任何重试** —— 分片走 `_ch.call`（30s 超时，失败即抛），
   `attachmentPut`（`lib/protocol/conversation.dart:387`）里一个 `try` 都没有，
   **任何一片失败整张图就废**。
3. **全串行** —— 多文件串行 × 分片串行双重串行。

### 量化后果（分片 384KB，按每片 1% 失败率，已属乐观）
| 场景 | 分片数 | 单图成功率 | 3 张全成 |
|---|---|---|---|
| 12MB 原图 | 32 | 72% | **38%** |
| 3MB 原图 | 8 | 92% | 78% |
| 压缩到 1MB | 3 | 97% | 91% |

**发 3 张照片超过一半概率失败。** 走 relay 跨网络时更糟。

### GitHub 学到的做法（已 fetch 验证）
- 分片重试必须**指数退避 + jitter**，只重试瞬时错误（超时/5xx），4xx 不重试
  （除 429），上限 5 次。
- **先压缩再传**是共识（`flutter_image_compress` 原生实现）。
- **流式读取**（`openRead`/`RandomAccessFile`）而非全量 `readAsBytes` ——
  现在每张图字节**在内存存两份**（`echo['attachments']` + `out`），多图易 OOM。
- 100MB 体积上限形同虚设（`f.size > 100 << 20`）。

### 方案（我建议的顺序）
- **P0**：①压缩（长边封顶 1600px + quality 82，12MB→约 800KB，32 片→3 片）
  ②分片重试（指数退避 + jitter，上限 5，只重试瞬时错误）
- **P1**：③多文件并发上传（限流 2~3）④流式读取 + 单份字节降内存
- **P2**：⑤断点续传（持久化 uploadId + 已传分片）

### ⚠️ 需要用户拍板的未决项
压缩有两条路，**决定要不要加依赖**：
- **A. 加 `flutter_image_compress`**：原生实现快（几十 ms），能编 JPEG 压得干净。
  **要加原生依赖**，有轻微构建风险。**我倾向 A。**
- **B. 用 Flutter 自带 `dart:ui`**：不加依赖，但 `toByteData` 只支持 PNG，
  压完仍偏大（3~5MB），收益打折。

**接手后别自己决定 A/B，先问用户。** 另外建议先向用户确认实际现象
（是"传不上去"还是"传上去不显示"），我的失败率分析是基于代码推算的。
